# AI Prompts & Workflow Log

This document tracks meaningful AI-assisted interactions throughout the development of the Sales CRM application.

## Workflow Structure
Each significant entry records:
- **Date - Prompt Number - Feature / Stage / Phase**
- **Problem / Task**: Objective and context of the interaction.
- **User Intent**: What the user was aiming to achieve.
- **Prompt given to ChatGPT (when relevant)**: Exploratory, architectural, or meta-prompting input provided to ChatGPT.
- **Important ChatGPT recommendation**: Architectural guidance, structured system instructions, or prompts generated by ChatGPT.
- **Actual prompt sent to IDE / Code Assistant**: The actionable prompt provided to the IDE code agent.
- **What IDE / Code Assistant implemented**: Exact code, configuration, or structural response provided.
- **Human review / testing**: How the implementation was verified.
- **Corrections or rejected suggestions**: Any changes made to AI suggestions, hallucinations, or anti-patterns.
- **Final outcome**: The end state of the task.

- **Problem / Task**: Establish project constraints, architectural boundaries, business rules, domain lifecycles, and documentation protocols before writing any code.
- **User Intent**: Provide the IDE code assistant with a crystal-clear, structured context from the project requirements, enforce single-tenant scope, module-based layered architecture, server-side authorization, immutable audit history, explicit tech stack, and mandatory incremental documentation across `architecture.md`, `schema.md`, `plan.md`, `decisions.md`, and `ai-prompts.md`.

  > *"I want to give the IDE code assistant full context of our Sales CRM project from the given README and requirements, and also give a clear idea about docs: what we need to document, how documentation must be maintained incrementally, and how to prevent it from jumping straight into generating premature code before establishing the foundation."*

  - Advised structuring a comprehensive Master Brief for the IDE code assistant divided into 14 distinct engineering sections.
  - Emphasized forbidding premature code generation, avoiding multi-tenant bloat, and enforcing strict server-side validation for deal lifecycle state transitions.
  - Outlined the exact document responsibilities (`architecture.md`, `schema.md`, `plan.md`, `decisions.md`, `ai-prompts.md`) and the rule to update docs incrementally per milestone rather than in a single bulk commit at the end.
- **Actual prompt sent to IDE / Code Assistant**:
  > Detailed 14-point initialization brief outlining:
  > 1. **Project Context**: Single-tenant Sales CRM for Busy Infotech with Manager and Sales Rep roles.
  > 2. **Engineering Philosophy**: Time-constrained assignment prioritizing correct business rules, server-side authorization, clean relational schema, maintainability, and zero unnecessary infrastructure (no Redis, Kafka, WebSockets, or microservices).

  > 8. **Execution Guardrail**: Explicit instruction to acknowledge understanding and pause without generating premature CRM code until project setup is instructed.
- **What IDE / Code Assistant implemented / responded**: Thoroughly reviewed all requirements, confirmed understanding of the domain boundaries, architecture, tech stack, and documentation workflow, and refrained from creating premature boilerplate code.
- **Human review / testing**: Verified that no unauthorized code or speculative schemas were generated and that the IDE assistant paused in the expected ready state.
